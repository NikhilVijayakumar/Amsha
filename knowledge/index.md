# Amsha knowledge bundle

Durable knowledge about the Amsha system: what each module is, what contracts
it honours, and why it is built the way it is.

This bundle is [OKF](https://openknowledge.sh/wiki/SPEC.html) v0.2 — a
directory of markdown files with YAML frontmatter. Every concept is
`type:` + prose, cross-linked with ordinary markdown links.

## Concepts

* [Features](features/) - The nine runtime modules under `src/nikhil/amsha/`, plus one retired
* [Methodology](methodology/) - The design-first stages, implementation guides, and change record
* [Contracts](contracts/) - Interfaces clients implement or depend on
* [Decisions](decisions/) - Choices with their rationale, so they survive the people who made them

## How to read this

**If you want to know what a module does**, read its feature concept. Start
with [crew-forge](features/crew-forge.md) — it is the entry point most client
applications touch.

**If you are about to change behaviour**, do not start here. Read
[methodology/proposal](methodology/proposal.md) and open a change under
`openspec/changes/`. This bundle is context for a change, not a place to
record one.

**If you are writing crew YAML**, this bundle is background. The
methodology is served by the MCP server — see
[methodology/implementation](methodology/implementation.md).

## Trust

Per OKF v0.2 §5.3, a concept with no `verified` entry reads as *unverified*;
one confirmed by a `human:` actor reads as *human-reviewed*. Every concept
here was generated by an agent from source and **carries no `verified`
entry**, because agent self-review is not independent confirmation. Each
carries `stale_after` instead, so a stale concept is detectable by date
rather than assumed fresh.

## Relationship to OpenSpec

| | This bundle | `openspec/` |
|---|---|---|
| Answers | What a module **is** | What behaviour **must be true** |
| Form | Prose | Requirements and scenarios, validated by `openspec validate` |
| Write here when | a module's role, boundaries, or rationale change | behaviour changes |

A concept links to its spec. Neither restates the other. See
[decisions/two-openspec-roots](decisions/two-openspec-roots.md).
